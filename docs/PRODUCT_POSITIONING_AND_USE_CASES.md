# Local Bridge 产品定位与个人、企业使用场景

> 产品决策：2026-10-27。本文是需求基线，不代表功能均已实现。0.1.0 目前提供只读 MCP、CloudFile 组件状态查询与离线 Profile 结构校验。

## 一、核心价值

**Local Bridge 是一个面向个人和企业的轻量级本地能力连接与任务协作平台。**

它在用户自己的电脑上，让原本割裂的个人通讯、企业 Web、云文件、本机 Office/CAD、MCP 和已有 AI Agent 自然协作。**成功不是管理多少能力，而是用户无需关心这些工具原来分属于不同系统。**

最高原则：**先解决用户真实痛点，不制造新障碍。** 尽量少复制、少上传下载、少切换、少登录、少重复配置；复用已有能力，真实任务闭环先于抽象框架。

- **一个 Runtime，个人与企业同时使用。** 企业 ApplicationProfile 和轻量个人工作空间共存，默认混合、按需隔离。
- **复用而不替代。** 企业认证和权限由原应用管理，文件操作由 CloudFile Agent2 管理，本机 AI 由已安装 Provider 运行，通讯由经用户许可的实际连接器提供。
- **用户选择工具。** WorkBuddy、Codex、Pi、MCP、微信等不应被强制替换为新的客户端；没有 Bridge 时已有 Web/文件入口不受影响。
- **安全不越界。** 不建企业 DLP、独立 IdP 或数据分类平台；Bridge 仍校验真实调用来源、受控能力、本机连接器许可和原服务的对象权限。

评审任何需求先问：**解决什么用户困扰？减少哪些步骤？复用哪些已有工具？是否带来新的障碍？**

## 二、共同核心诉求

| 用户困扰 | 期望能力 | 不要增加 |
|---|---|---|
| 消息 → AI → 文件 → 软件 → 回复需要大量复制粘贴 | 同一任务跨应用交接上下文、状态和用户选择的数据 | 额外数据搬运/审批工作流 |
| 企业网页已登录，本机仍要求重复认证 | 浏览器原 Session 申请范围票据，无感交给本机 | Bridge 自有登录/读取 Cookie |
| 电脑已有多个 Agent 和 MCP，却彼此割裂 | 发现真实可用工具、选择 Provider、调用并返回结果 | 自研全功能 AI 聊天客户端 |
| 多个系统的任务无法一起看 | BridgeTask 关联真实状态、结果和下一步动作 | 第二套文件/聊天/AI 事实账本 |
| 同一台电脑使用个人和企业资源 | 默认混合，共享已授权能力；需要时用户可选独立 | 默认 Profile 数据墙/跨域审批 |
| 外部系统回执未知 | 查询原操作并如实展示 unknown | 盲目重发或把已受理当完成 |

## 三、企业场景与核心诉求

| ID | 场景 | 现实痛点 | 验收目标 |
|---|---|---|---|
| E1 | Etech / CloudFile → 本地查看、普通编辑、独占编辑 | Web 与 Word/Excel/专业软件割裂，下载/上传繁琐 | 保留 Agent2 + Hub/Server 原授权、Journal、Guard 和文件版本；真实文件操作不因 Bridge 损坏 |
| E2 | 图纸/Office/CAD 专业应用 | Web 无法便捷打开本机已安装软件 | 复用原系统打开规则；不许诺多文件 CAD 工程自动同步 |
| E3 | Etech 元枢原 Web 调用本机 MCP 与 Agent | 企业 Web AI 难用本机工具 | 保留原元枢 UI、SSO 和 AI API；一个只读 MCP 与一个经许可 Agent run 返回真实结果 |
| E4 | Etech SSO、CloudFile + Authentik、其他 IdP | 重复登录及重复维护账号 | 已登录 Chrome 经应用后端取得短期操作票据；Bridge 无需识别每种企业 SSO |
| E5 | 文件与企业业务任务 | 多窗口完成后无法追踪/恢复 | 统一任务视图，真实业务和权限仍由拥有它的服务判断 |

**企业最核心的要求：** 兼容已有系统；操作可靠、无感；零/低增量配置；不破坏 CloudFile 生产文件主链；不用建设一套新的企业安全平台。

## 四、个人场景与核心诉求

| ID | 场景 | 现实痛点 | 验收目标 |
|---|---|---|---|
| P1 | 本机 Codex / WorkBuddy / Pi 与 MCP | 已有 AI 工具孤立、难切换与查询结果 | 默认本地个人工作空间，发现已安装且真正授权可调用的 Provider，完成一次 run |
| P2 | 个人微信/微信群及 Soul 等聊天助手 | 手动复制消息、群任务整理和待办 | 经用户许可的真实本地 Connector 读取选定会话、订阅新增消息、交给本机 Agent |
| P3 | 消息回复、任务通知 | AI 给出结果后还要复制回聊天软件 | 生成草稿或在用户设置的会话/规则范围内发送，并查询原发送状态 |
| P4 | 个人文件、本机应用 | 本地文档和专业工具难供 AI 使用 | 用户本机许可下复用 Office、文件与工具，不强制企业 CloudFile 账号 |
| P5 | 个人任务中心 | Agent/聊天任务没有统一入口 | 显示来源、真实状态和用户下一步操作 |

**个人最核心的要求：** 不要求 Bridge 云账号、厂商独占或新复杂安装；用户自主决定本机工具和通讯连接器；在连接器确实支持时提供完整双向消息能力。

微信、Soul 等是用户场景，不代表官方个人私聊 API 一定存在，更不代表 Bridge 已实现。可用性取决于实际安装的软件、第三方适配能力、平台规则及隐私约束；Bridge 不内置私有协议绕过机制。

## 五、个人与企业同时存在：必须原生支持

**典型场景：** 公司 Windows/macOS 电脑上已登录 Etech/CloudFile，同时登录个人微信。员工既要本机查看/编辑企业 Word/CAD，又要让个人微信助手获取指定群消息、交给本机 AI 处理。

| ID | 协作流程 | 期望体验 |
|---|---|---|
| M1 | CloudFile 文件编辑与个人微信消息订阅并行 | 一个 Bridge/任务中心，不切换个人或企业模式，现有编辑不中断 |
| M2 | 个人微信需求 → 本地 Agent → CloudFile 文档 | 已授权的文件工具可直接参与协作；不增加 Bridge 的跨 Profile 审批，CloudFile 仍终判权限 |
| M3 | 企业文件处理结果 → 通讯连接器 → 同事 | 用户选择输出及发送规则；原 Connector 返回真实送达/未知状态 |
| M4 | Etech 已登录元枢 → 用户已有 Codex/WorkBuddy/Pi | 不必安装另一个企业 Agent、不新建 AI 登录 |
| M5 | 用户要求隔离某些工作空间 | 由用户开启可选的 Bridge 本地路由隔离，不默认阻止混合协作，也不声称是操作系统沙箱 |

**设计结论：默认混合，按需隔离。** Profile 是身份、来源与任务归属标记，不是默认的数据墙；企业 Dev/Prod Host、凭据、Journal 和文件工作副本仍应独立，以免错误执行。共享已授权能力并不等于网页/聊天文本能自行获得本机任意操作权。

## 六、近期真实验收而非平台工程

1. 企业 E1：现有 CloudFile 文件三模式不变；Bridge 在 DEV 先旁路读任务状态。
2. 个人 P1/P2：至少一条真实本机 Agent 调用、一种用户许可的通讯连接器读消息/事件 → Agent → 返回结果。发送按真实能力逐步验收。
3. 混合 M1/M2：同机企业文件任务和个人通讯任务并存、统一展示，跨工具正常协作且不额外增加 Profile 审批。
4. 失败/缺失降级：Bridge、Agent、Connector 或 Web 登录缺失时正确提示，原应用仍可使用。
